\section{Expressiveness of Mapping Algebra}%
\label{sec:expressiveness}
After establishing the formalism of our mapping algebra in
Section~\ref{sec:mapping_algebra}, we demonstrate its expressiveness by using
it to define the semantics of the RML mapping language, specifically version
1.1.2~\footnote{\url{https://rml.io/specs/rml/v/1.1.2/}}.
This section provides an algorithm that, given a valid arbitrary 
{\color{blue}RDF graph representing an RML document},
generates an algebraic expression that captures the semantics of the mapping
process
	\todo{I don't think that an RML document describes a "mapping process". Instead, it defines a mapping.}
described in the input RML document.
We demonstrate that our mapping algebra is \textbf{at least as expressive as} RML, and 
provide a \textbf{well-defined formal semantics} for RML v1.1.2. 

\subsection{Translation Preliminaries}%
\label{sub:translation_preliminaries}
Before translating an RML document into our algebraic expression, a few
preparations are required: i)~normalization of the RML document,
ii)~identification of RDF sub-graph to translate algebraic expressions relevant
to a specific triples map, and iii)~definitions of extend functions for Extend
operator creation.



\subsubsection{RML normalization}%
\label{ssub:rml_normalization}
First, the input RML document
	\todo{Again, the input to our normalization procedure is not an "RML document".}
is \emph{normalized} by applying the following sequence of rewriting steps. We have adopted these steps from Rodríguez-Muro and Rezk~\cite{Mariano2015SPARQL2SQL}, with adaptations specific to RML. None of these steps changes the meaning of the defined mapping.
	\todo{TODO: explicitly refer to the SPARQL Update queries in Appendix~\ref{appdx:queries}.}
\begin{enumerate}
	\item
	\label{item:NormalizationStep:ClassExpansion}
	Every \ttl{rr:class} definition is expanded into a predicate-object map.

	\item
	\label{item:NormalizationStep:ConstantsExpansion}
	All shortcuts for constant-valued term maps are expanded.

	\item
	\label{item:NormalizationStep:POMDuplication}
	Predicate-object maps with multiple predicate maps or multiple object maps are duplicated to have a single predicate map and a single object map each.

	\item
	\label{item:NormalizationStep:JoinRemoval}
	Referencing object maps without a join condition are replaced by an object map with the subject IRI of the parent triples map as the reference value.

	\item
	\label{item:NormalizationStep:TMDuplication1}
	Every triples map with multiple predicate-object maps is duplicated such that each of the resulting triples maps has a single predicate-object map~only.

	\item
	\label{item:NormalizationStep:TMDuplication2}
	Every triples map with multiple graph maps is duplicated such that each of the resulting triples maps has one of these graph maps.
\end{enumerate}
%
After normalizations, all triples map in the normalized RML document have only
a single predicate-object map and if present, a single graph map. 
Moreover, all term maps do not have shortcuts. 
Normalizing the RML document reduces the complexity when parsing the RML
document by simplifying complex triples maps. 

\subsubsection{Triples Map-specific RDF Graph}%
\label{ssub:tm_specific_rdf_graph}
Secondly, to support the translation process, we define two types of RDF
graphs within an RML document: i)~\textbf{$\triplesMapIRI$-specific triples map
graph}, and ii)~\textbf{$\triplesMapIRI$-specific parent triples map graph}. 
\textbf{$\triplesMapIRI$-specific triples map graph} contains all triples describing 
the given triples map $\triplesMapIRI$, while  
\textbf{$\triplesMapIRI$-specific parent triples map graph} contains triples 
from all triples map $\triplesMapIRI'$ that refers to $\triplesMapIRI$ for 
creating join relations. 
Together, both RDF graph are used to translate relevant algebraic expressions 
for the mapping described by the triples map $\triplesMapIRI$.

\subsubsection{Relevant Extension Functions}%
\label{ssub:built_in_extend_functions}
Lastly, we define the following extension functions~(as per Definition~\ref{def:ExtensionFunction})
to support the creation of Extend operators during the translation 
of RML descriptions into our formalism. 
Most of the extend functions are used for type casting the RDF terms for the 
generation of RDF datasets.
The extend function $\concat$ is used in
Algorithm~\ref{alg:template_function} to resolve the template string
according to the RML
specification~\footnote{\url{https://rml.io/specs/rml/\#from-template}}. 
	\todo{TODO: remove the formal parts of the following definitions and refer to Appendix~\ref{appdx:functions} for the formal definitions.}
\begin{itemize}
	\item
	$\toIRI$ is a unary extension function that converts string literals representing IRIs into these IRIs. Formally,  for every $v \in (\symTermUniverse \cup \error)$, we define:
\begin{equation*}
	\fctToIRI{v} =
	\begin{cases}
		\mathit{lex}
		& \text{if $v$ is a literal $\literalTuple$ such that $\lex$ is a valid IRI}
		\\[-2mm]
		& \text{and $\dt$ is the IRI \texttt{xsd:string},}
		\\
		\error
		& \text{else.}
	\end{cases}
\end{equation*}

	\item
	$\toBNode$ is a unary extension function for which we assume a function $\LTB: \symAllLiterals \rightarrow \symAllBNodes$ that is injective. Then, $\toBNode$ uses $\LTB$ to convert string literals into blank nodes. Formally, for every $v \in (\symTermUniverse \cup \error)$, we define:
\begin{equation*}
	\fctToBNode{v} =
	\begin{cases}
		\LTB(\lex)
		& \text{if $v$ is a literal $\literalTuple$ such that $\dt$ is the IRI \texttt{xsd:string},}
        \\ 
		\error
		& \text{else.}
	\end{cases}
\end{equation*}

	\item
	$\toLiteral$ is a binary extension function that converts string literals into literals with a datatype IRI that is given as the second argument. Formally, for every pair $(v, \dt)\in (\symTermUniverse \cup \error) \times (\symTermUniverse \cup \error)$, we define:
\begin{equation*}
    \fctToLiteral{v, \dt} = 
    \begin{cases}
        (\lex, \dt) &\text{if $v$ is a literal~$(\lex, \dt')$ such that $\dt'$ is the IRI \texttt{xsd:string}}, \\
        \error & \text{else.}
    \end{cases}
\end{equation*}

	\item
	$\concat$ is a binary extension function that concatenates two string literals. Formally, for every pair $(v_1, v_2) \in (\symTermUniverse \cup \error) \times (\symTermUniverse \cup \error)$, we define,
\begin{equation*}
    \fctConcat{v_1}{v_2} = 
    \begin{cases}
        (\lex_1 \circ \lex_2, \texttt{xsd:string})  &\text{if $v_1$ and $v_2$ are literals $(\lex_1,\dt_1)$ and}
		\\[-1mm]
        & \text{$(\lex_2,\dt_2)$, respectively, such that both}
		\\[-1mm]
        & \text{$\dt_1$ and $\dt_2$ are the IRI \texttt{xsd:string},}
        \\ 
        \error &\text{else,}
		\\
    \end{cases}
\end{equation*}
where $\lex_1 \circ \lex_2$ is the string obtained from concatenating the strings $\lex_1$ and $\lex_2$.
\end{itemize}

			%such that
			s.t.\

In RML, there are three ways to map data to RDF terms using RML term maps; 
i) \textbf{constant-valued}~\footnote{\url{https://rml.io/specs/rml/\#constant}} term map, 
ii) \textbf{reference-valued}~\footnote{\url{https://rml.io/specs/rml/\#reference}} term map, and
iii) \textbf{template-valued}~\footnote{\url{https://rml.io/specs/rml/\#from-template}} term map. 
During the RML translation process, extend expressions are translated from 
these term maps to create new RDF terms as follows. 
A constant-valued term map contains a triple $(s,\ttl{rr:constant},o)$, and 
the extend expression translated from this term map is the object RDF term $o$. 
A reference-valued term map contains a triple $(s,\ttl{rr:reference},(\lex,\ttl{xsd:string}))$ where 
the string value $\lex$ is the query to retrieve the value for the RDF term. 
Given a map~$\symAttrQueryMap$ that associates the attributes with the queries,
the extend expression translated from a reference-valued term map is the
attribute value $\attr$ such that $\symAttrQueryMap(\attr) = \lex$.

For the translation of extend expression from template-valued term map containing  
a triple $(s,\ttl{rr:template},(\lex,\ttl{xsd:string}))$, we provide a
definition for the semantics of processing the template string $\lex$ as
follows. 

\begin{definition}
    \label{def:tempSubStrs}
    \normalfont
    Let $v = (\lex, \dt)$ an input literal string such that $\dt$ is \texttt{xsd:string}.  
    For ease of reading, we call a substring of $\lex$ an \textbf{enclosed query substring} 
    if it is the substring starting and ending with the curly braces \{ and \} respectively, as defined in 
    RML specification, 
    otherwise it is called as \textbf{normal substring}.
    $\tempSubStrs$ is a unary function which splits $\lex$ into a sequence~$\substrSeq$
    of substrings of $\lex$ that contains alternating normal substrings and
    enclosed query substrings in two pass as follows: 
    \begin{enumerate}
        \item  An intermediate sequence~$\substrSeq'$ of substrings is generated that 
            contains substrings that are \textbf{normal} or \textbf{enclosed query}  
            substrings in the order that these substrings appear in $\lex$ from 
            left to right. 
        \item $\substrSeq'$ is further processed as follows to produce $\substrSeq$: 
            \begin{enumerate}
                \item If $\substrSeq'$ is empty, a new empty substring is inserted into $\substrSeq'$.
                \item For every two enclosed query substrings that occur directly after one another in $\substrSeq'$, a new empty substring is inserted into $\substrSeq'$ in between these two enclosed query substrings.
                \item If the first element in $\substrSeq'$ is an enclosed query substring, 
                    a new empty substring is inserted into $\substrSeq'$ as the new first substring.
                \item If the last element in $\substrSeq'$ is an enclosed query substring, 
                    a new empty substring is appended to the end of $\substrSeq'$.
            \end{enumerate}
    \end{enumerate}
\end{definition}

After the aforementioned processing, $\substrSeq$ is an
alternating sequence of normal substrings and enclosed query substrings
with the enclosed query substrings at every second position, and $\substrSeq$ 
is not empty and has an odd number of elements.
$\substrSeq$ is used to generate the extend expression consisting of 
$\concat$ functions where each enclosed query substrings, $\queryExpr$, are 
replaced with an attribute $\attr$ such that $\symAttrQueryMap(\attr) = \queryExpr$. 
The result is the extend expression translated from the template-valued term map, 
and we provide the pseudocode code in Algorithm~\ref{alg:template_function}.

\begin{algorithm}[htbp]
	\caption{\textsc{Template}:
		%Creates an extend expression for resolving an IRI template.}
		%Creates an extend expression to resolve an IRI template.}
		%Creates extend expressions for resolving IRI templates.}
		Creates extend expressions to resolve IRI templates.}
	\label{alg:template_function}
	\begin{algorithmic}[1]
        \Require \textit{tmpl} - a string (assumed to be an RML string template)
        \Statex \qquad $\symAttrQueryMap$ - an injective partial function that maps attributes to query expressions
		\Ensure an extend expression (as per Definition~\ref{def:ExtendExpressions:Syntax})
        \State $\substrSeq \gets \fctTempSubStrs{\textit{tmpl}}$ \Comment Definition~\ref{def:tempSubStrs}
        \State $\extExpr \gets (s_1, \texttt{xsd:string})$, where $s_1$ is the first element in $\substrSeq$
        \If{$|\substrSeq| > 1$}
            \ForAll {$i = 2,\dots,|\substrSeq|$}
                \State $s_i \gets $
                    the $i$-th element in $\substrSeq$
                \If{$s_i$ is a string that starts with "\{" and ends with "\}"}
                    \State $\extExpr \gets \fctConcatBig{\extExpr}{\symAttrQueryMap^{-1}(\queryExpr)}$, where $\queryExpr$ is
	                    %the substring of
                    $s_i$ without the enclosing "\{" and "\}"
                \Else
                    \State $\extExpr \gets \fctConcatBig{\extExpr}{(s_i, \texttt{xsd:string})}$
                \EndIf
		    \EndFor
        \EndIf
		\State \Return $\extExpr$
	\end{algorithmic}
\end{algorithm}
Now we have all the ingredients to translate any given RML document to our 
algebraic expressions. 

\subsection{Translation Algorithms}%
\label{sub:translation_algorithms}
We present the pseudocode of the algorithm to translate a normalized RML document 
to algebraic expressions in Algorithm~\ref{alg:rml2algebra}. 
Given an RDF graph of a \emph{normalized} RML document and for each triples map
in the RDF graph, the algorithm first generates a Source operator 
following Algorithm~\ref{alg:rml_source_op} where all the query expressions
detected in the current triples map-specific RDF
graph~(Section~\ref{ssub:tm_specific_rdf_graph}), are extracted
(Algorithm~\ref{alg:query_extraction}) and composed to form the current 
algebraic expression being translated~$\omega'$. 
Subsequently, the relevant Extend operators are extracted, according to 
Algorithm~\ref{alg:rml_termmap_extend_expr}, for both the subject and the 
predicate term maps (line 6-11) where the Extend operators generate the 
subject and predicate terms while binding them to the attributes $\subjAttr$ and $\predAttr$ 
respectively. 

To extract the Extend operators from the object maps, we need to also
determine if it is a referencing-object
map~\footnote{\url{https://rml.io/specs/rml/\#logical-join}}. 
If the object map is a referencing-object map (line 14-28), the algorithm first
extracts the Source operator for the parent triples map (line 15-18) and stores
it into a temporary algebraic expression~$\omega_{ptm}$, retrieves the
join attributes (line 20-24) for the Equi-join operator (line 25), and finally,
the algebraic expression~$\omega'$ is updated with the Equi-join operator by joining
with $\omega_{ptm}$(line
26-28).
Otherwise, the object map is treated the same as the subject and the predicate map 
where an Extend operator is extracted directly (line 30-31). 
The Extend operator generated for the object map binds the value returned by 
evaluating the extend expression to the attribute $\objAttr$. 

To determine the RDF graph of the triples to be generated, 
an Extend operator, to generate the graph IRI, is generated from the graph map 
that exists in the triples map (line 33-36). 
If there is no graph map in the triples map, a default graph IRI is generated 
with the value \texttt{rr:defaultGraph} (line 37-38). 
The attribute $\graphAttr$ contains the graph IRI to be generated by the 
Extend operator. 

Finally, a Projection operator is applied to restrict the mapping relations to 
the attributes 
$\subjAttr, \predAttr, \objAttr$, and $\graphAttr$, for the generation of 
an RDF dataset as per Definition~\ref{def:generated_dataset} (line 40-41). 
To capture all the mappings described in the RML document, a Union operator 
is applied between the accumulated expression~$\omega$ and the current 
algebraic expression~$\omega'$ (line 42). 
At the end of this algorithm, we have an algebraic expression $\omega$ that 
captures the full semantics of the mapping process described in a given 
normalized RML document.

	\caption{QueryInTriplesMap: Extract query expressions from RML triples maps}
	\label{alg:query_extraction}
	\begin{algorithmic}[1]
		\Require  $\symRMLGraph$ an RDF graph of RML document,
		\Statex  \qquad $\triplesMapIRI$ the subject IRI of a triples map
		\Ensure  A set of query expressions

		\State $\symDataAcc \gets \emptyset$ \Comment Initially empty set of query expressions
		\For{$(s,p ,o) \in \triplesMapGraph{TM}{\triplesMapIRI}$ s.t.\ $p$ is the IRI \texttt{rml:reference} and $o$ is a literal $(\lex,\dt) \in \symAllLiterals$}
		    \State $\symDataAcc \gets \symDataAcc \cup \{ \lex \}$
		\EndFor
		\For{$(s,p ,o) \in \triplesMapGraph{TM}{\triplesMapIRI}$ such that $p$ is the IRI \texttt{rr:template} and  $o$ is a literal $(\lex,\dt) \in \symAllLiterals$}
		    \State $\symDataAcc' \gets$ set of all substrings in $\lex$ that are enclosed by \{ and \}
		    \State $\symDataAcc \gets \symDataAcc \cup \symDataAcc'$
		\EndFor
		\State $T_\textrm{child} \gets \{ (s,p,o) \in \triplesMapGraph{TM}{\triplesMapIRI} \, | \, p \text{ is the IRI } \texttt{rr:child} \}$
		\State $T_\textrm{parent} \gets \{(s,p,o) \in \triplesMapGraph{PTM}{\triplesMapIRI} \, | \, p \text{ is the IRI } \texttt{rr:parent} \}$
		\For{$(s,p,o) \in (T_\textrm{child} \cup T_\textrm{parent})$ such that $o$ is a literal $(\lex,\dt) \in \symAllLiterals$ }
		    \State $\symDataAcc \gets \symDataAcc \cup \{ \lex \}$
		\EndFor
		\State \Return $\symDataAcc$
	\end{algorithmic}
\end{algorithm}


\begin{algorithm}[htbp]
	\caption{\textsc{TranslateSourceOperator}: Source operator translation for a given triples map IRI $\triplesMapIRI$}
	\label{alg:rml_source_op}
	\begin{algorithmic}[1]
		\Require $\triplesMapIRI$ subject IRI of a triples map
		\Statex \qquad $\symRMLGraph$ an RDF graph of RML document
		\Ensure A tuple containing query expression and a partial function $\symAttrUniverse  \rightarrow  \symDataAcc$
		\State $ls_{iri} \gets o$ for a triple $(s,p,o) \in \symRMLGraph$ where $s = \triplesMapIRI$  and $p= \texttt{rml:logicalSource}$
		\State $\queryExpr \gets o$ for a triple $(s,p,o) \in \symRMLGraph$ where $s = ls_{iri}$  and $p=  \texttt{rml:iterator }$
		\State $\symDataAcc \gets$ \textbf{QueryInTriplesMap}($\triplesMapIRI, \symRMLGraph$) \Comment{Algorithm~\ref{alg:query_extraction}}
		\State $\symAttrQueryMap \gets$ initially empty function from attributes to query expressions in $\symDataAcc$
		\For{$\queryExpr' \in \symDataAcc$}
		\State $\attr \gets$ a fresh attribute from $\symAttrUniverse \setminus \{ \attr_\textrm{s}, \attr_\textrm{p}, \attr_\textrm{o}, \attr_\textrm{g} \}$ that has not been used before in this translation process
		\State $\symAttrQueryMap \gets \symAttrQueryMap \cup \{ a \rightarrow \queryExpr' \}$
		\EndFor
		\State \Return  $(\queryExpr, \symAttrQueryMap)$
	\end{algorithmic}
\end{algorithm}

\begin{definition}
    \label{def:init_data_source}
    Let $ls_{iri}$ be an IRI of an RML logical source. 
    We denote $\fctInitSrc{ls_{iri}}$ as a \textbf{data source}, $\dataSourceTuple$, derived 
    from the configurations of the given logical source~$ls_{iri}$.
\end{definition}
For example, given an RDF graph~$\symRMLGraph$ of an RML document in Listing~\ref{lst:rml_document}, 
and a triple $(s, \texttt{rml:logicalSource}, ls_{iri}) \in \symRMLGraph$, 
$\fctInitSrc{ls_{iri}}$ returns a data source tuple, $\dataSourceTuple$, such 
that $\bigDataObject$ is a CSV dataset from the file ``sport.csv" and 
$\sourceType =  \sourceTypeTuple$ such that  $\symSetDataset$ is a set of  
CSV datasets, $\symDataAcc$ a set of all possible query expressions applicable to the 
given CSV dataset, such as column names.
$\eval$ is a function that returns a row of CSV data object per
iteration, and $\cbeval$ is a function that returns the data object for the
given CSV column name.
